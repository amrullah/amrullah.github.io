- The [[Architecture]] of a system is the set of fundamental concepts or properties of the system in it's environment, embodies in it's ^^elements^^, ^^relationships^^ and ^^principles of it's design and evolution^^.
- # Software Architecture
    - Computers can be found everywhere in modern society. All computer systems are made up of the same 3 fundamental parts: Software (programs, libraries), Data (which may be either transient or persistent) and Hardware (processors, memory, disks, network cards). When you try to understand  a system, you are interested in
        - what it's individual parts actually do,
        - how they work together
        - how they interact with the world around them
    - The Architecture of a system is the set of fundamental concepts or properties of the system in it's environment, embodied in it's elements, relationships and principles of it's design and evolution #definition
    - ## System Elements and Relationships
        - Elements are an architecturally significant pieces of a system. The elements that constitute a system and the relationships between them define the structure of the system that contains them. There are two types of structures that are of interest to the [[Software Architect]]
        - ### Static Structures
            - The static structures of a system define the internal design-time elements and their arrangement #definition
            - The static structures of a system tell you what the ^^design-time^^ form of a system is, ie. what the ^^elements^^ are and how they combine to provide the features required of a system.
            - #### Kinds of elements
                - Internal design-time ^^software elements^^ might be programs, object-oriented classes or packages, database stored procedures, services or any other self-contained code unit.
                - Internal ^^data elements^^ include classes, relational database entities/tables and data files.
                - Internal ^^hardware elements^^ include computers or their constituent parts such as Disk or CPU and networking elements such as cables, routers or hubs. #intriguing
            - The static arrangement of these elements defines (depending on the context) the ^^associations^^, ^^relationships^^ or ^^connectivity^^ between these elements.
                - Examples: object hierarchy, dependency, linkage (has-a relationship or Foreign Key reference) or physical interconnections between hardware devices.
        - ### Dynamic structures
            - The dynamic structures of a system define it's ^^runtime elements^^ and their ^^interactions^^ #definition
            - The system's dynamic structures show how the system actually works, ie. what happens at runtime and what the system does in response to external (or internal) stimulus
            - Internal interactions may be:
              id:: 67cc36a9-7e10-407c-a3e1-02f433268006
                - flows of information between elements (eg. message passing).
                - parallel or sequential execution of internal tasks
                - effect on data (data item D is created, updated many times and finally destroyed)
        - A system's static and dynamic structures are ^^closely related^^ to one another. However the two structures are not the same.
            - Consider a simple client/server system with one client facing element that handles all interactions with users. This would appear ^^once^^ as a ^^static^^ structure element, but would appear ^^many times^^ (once per active user) in a ^^dynamic^^ structure model.
    - ## Fundamental System Properties
        - The fundamental properties of a system manifest themselves in two different ways:
            - ### Externally visible behavior
                - Tells you ^^what a system does^^ from the standpoint of an ^^external observer^^
                - The externally visible behavior of a system defines the ^^functional interactions^^ between the system and it's environment #definition
                - Kinds of external interactions: (quite similar to ((67cc36a9-7e10-407c-a3e1-02f433268006)))
                    - flows of information, in and out of the system
                    - the way the system responds to external stimuli and published "contract" or API that the architecture has with the outside world.
                - External behavior may be modeled by treating the system as a black-box (Example: if you make request P, you are returned response Q). Alternatively, it may consider change to the internal state (submitting a request R causes the creation of an internal data item D).
            - ### Quality properties - (how the system does it)
                - Tell you ^^how a system behaves^^ from the viewpoint of an ^^external observer^^ (often referred to as it's ^^non-functional characteristics^^)
                - A quality property is an externally visible, non-functional property of a system such as it's Performance, security or scalability.
                - [[Software Quality Attributes]]
                - Examples:
                    - How does the system perform under load?
                    - What is the peak throughput given certain hardware?
                    - How is the information in the system protected from malicious use?
                    - How often is it likely to break?
                    - How easy is it to manage, maintain and enhance?
                    - How easily can it be used by people who are disabled?
                - Which of these characteristics are relevant depends on your circumstances and on the concerns and priorities of your [[stakeholders]]
    - ## Principles of Design and Evolution
        - One of the things that is immediately obvious about a ^^well-structured^^ and ^^maintainable^^ system is that it's implementation is ^^consistent^^ and respects a ^^system-wide^^ set of structuring ^^conventions^^. This allows the system to be more ^^easily understood^^ and encourages ^^extensions^^ to the system to be made in a ^^consistent^^ and ^^logical^^ way, fitting into the overall form of the system.
        - One of the things that is ^^necessary^^ in order to achieve the ^^internal implementation consistency^^ is a ^^clear set of principles^^ to guide the system's ^^design^^ and ^^evolution^^.
        - ### Architectural Principles
            - Fundamental statement of belief, approach or intent that guides the definition of your Architecture #definition
            - Defining and following architectural principles is a powerful way of establishing a ^^decision-making framework^^ for a consistent, well-structured architecture. Principles expose the implicit underlying assumptions explicit.
            - They are a great way to kick off an architecture project, especially when motivation or scope is unclear. They are also useful if you suspect that there are significant but unrecognized ^^conflicts^^ or ^^contradictions^^ in the ^^requirements^^ of a proposed architecture
    - ## System Properties and Internal Organization
      collapsed:: true
        - We can capture the relationship between the externally visible properties of a system and it's internal structure and organization as follows:
            - The externally visible behavior of a system is determined by the combined functional behavior of it's internal elements.
            - The quality properties of a system (such as performance, scalability, resilience etc.) arise from the quality properties of it's internal elements. Typically a system's overall quality property is only as good as it's weakest internal element's property.
        - ### Candidate Architecture
            - It is a particular arrangement of static and dynamic structures that has the potential to exhibit the system's required externally visible behaviors and quality properties. #definition
            - Although Candidate Architectures have different static and dynamic structures, each must be able to meet the system's overall required externally visible behaviors. But it is likely that these candidate architectures will differ in specific set of quality properties that they will exhibit.
            - The extent to which the candidate actually exhibits these behaviors and properties must be determined by further analysis of it's static and dynamic structures.
            - It is part of the architect's role to derive the static and dynamic structures for each of the candidate architectures, understand the extent to which they exhibit the required behaviors and quality properties and select the best one.
- # Architectural Elements
    - It is a fundamental piece from which a system can be considered to be constructed. #definition
    - The nature of an architectural element depends very much on the type of system you are considering and the context within which you are considering it's elements. Programming libraries, subsystems, deployable software units (eg. EJB or .NET assemblies), reusable software products, or entire applications may form architectural elements in an information system.
    - An architectural element should possess the following key attributes:
        - A clearly defines set of ^^responsibilities^^.
        - A clearly defined ^^boundary^^.
        - A set of clearly defined ^^interfaces^^, which define the ^^services^^ that the element provides to the other architectural elements.
- # Stakeholders
    - A stakeholder in the architecture of a system is an individual, team, organization or classes thereof, having an interest in the realization of the system #definition
    - ## Individual, Team or Organization
        - Those with an interest in the architecture of a system stretch far more widely then just it's developers and users. It also includes those who have to support it, deploy it or pay for it.
        - Specifying architecture is a key opportunity for the stakeholders to direct it's shape and direction. Part of your role is to engage and galvanize, to persuade people of importance for their involvement and to obtain their commitment to the task.
        - A stakeholder often represents a class of individual, such as user or developer, rather than a specific person, which means it may not be possible to capture and reconcile the needs of all members of the class in reasonable time. In that case, you need to select some representative stakeholders who will speak for the group.
    - ## Interests and Concerns
        - A concern about an architecture is a requirement, an objective, a constraint, an intention or an aspiration a stakeholder has for that architecture. #definition
        - As you start to develop your architecture, you are engage in a process of ^^discovery^^ as much as one of ^^capture^^.  Ie. early in the development lifecycle, your stakeholders may not yet precisely know what their requirements are.
        - Many concerns will be common among stakeholders, but some concerns will be distinct and may even conflict. resolving such conflicts in a way that leaves stakeholders satisfied can be a significant challenge.
    - ## The Importance of Stakeholders
        - Stakeholders explicitly or implicitly drive the whole shape and direction of the architecture, which is solely created for their benefit and to serve their needs.
        - Stakeholders ultimately make or direct the fundamental decisions about the scope, functionality, operational characteristics and structure of the eventual product or system.
        - Architectures must be evaluated with respect to the stakeholder needs as well as abstract architectural and [[Software Engineering]] principles.
- # Architectural Description
    - AD is a set of products that ^^documents^^ an architecture in a way it's stakeholders can understand and ^^demonstrates^^ that the architecture has met their concerns. #definition
    - An architecture for a software system can be an incredibly complex thing. Part of the architect's role is to describe this complexity to people who need to understand it.
    - "Products" in this context can mean a range of things:
        - Architectural models
        - scope definitions
        - constraints
        - principles
    - A description of an architecture has to present it's essence and it's detail at the same time. It must provide an overall picture that summarizes the whole system, but it also must decompose into enough detail that it can be validated and the described system can be built.
    - A [[Software Architect]] who writes the AD, uses it as a memory aid, a basis for analysis ,  a record of decisions and so one.
- # Relationships between the Core Concepts
    - Relationships
        - A system is built to address the needs, concerns, goals and objectives of it's stakeholders.
        - The architecture of a system comprises of a number of architectural elements and their inter-element relationships.
        - The architecture of a system can be potentially be documented by an AD (fully, partially or not at all). There are many potential ADs for a given architecture, some good, some bad.
        - An AD documents an architecture for it's stakeholders and demonstrates to them that it has met their needs
