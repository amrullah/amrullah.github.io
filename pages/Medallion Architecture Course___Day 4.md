- [[Metadata Management]] ((68e3be1e-2eb9-463d-afa3-2b905b35eb65)).
    - present in the following places:
        - `json` file,
        - in [[Parquet]] files and
        - even in the directory (for eg. date based folder partition)
        - `checkpoint.parquet` file
            - An optimization over commits is the concept of checkpointing, which reduces the number of json files to be opened, thereby reducing the disk random access, which is detrimental to [[Performance]]
            - Even though it's a [[Parquet]] file, it stays in the `_delta_log` folder, with the `json` files.
            - [Code Example](..assets/AD_databricks-samples-main/Basic-deltatable-creation/Basic_delta_plus_Checkpoint.ipynb)
        - [[Unity Catalog]] , [[Hive Metastore]]
    - [[Data Discovery]] and [[Data Governance]]
        - Enables the Data consumers to find and trust the right tables
            - All your tables, views, schemas, partitions etc.
        - Drives [[Data Lineage]], [[Access Control]], [[Auditing]]
            - Who owns them, who has what kind of access
    - [[Performance Optimization]]
        - Partition and File level statistics let the engine prune the data and choose efficient query plans
            - Remember, the actual data goes in [[Parquet]] files and the metadata goes in `json` files. Its this metadata that is used for query optimization
    - [[Schema Evolution]] and [[Schema Enforcement]]
        - Tracks column additions, type-changes, defaults etc.
    - [[Auditability]] and reproducibility
        - Immutable transaction log which records every append or update
        - History of all writes / updates supports debugging and [[Compliance]]
        - Rewind the table to a previous version for debugging or running a query
        - Debugging when bad data was introduced, which job processed that data

- [[Metadata Management]] techniques ((68e3c50e-47d7-44c8-a7dc-a0b7afdb9c3e))
    - Pure [[Delta Lake]]
    - [[Hive Metastore]]
        - Was used for quite a long period, since [[Apache Hadoop]] days
    - [[Unity Catalog]]
        - Comparitively new concept introduced by [[DataBricks]]
        - Cloud-first
        - Goal: Unified governance the data and [[AI]] assets, [[Hive Metastore]] was focused only on data
            - Even outside the [[DataBricks]], could even be of data from an external cloud!
        - Acts as Control Plane
            - (json and parquet files act as Data Plane)
    - Comparison of various techniques ((68e3c777-dac7-4275-ad0e-8aaa7af5ee36))
    - Best Practices ((68e3c7b5-d14e-4fcb-a6ef-b5960f772ed6))
        - Always Register Production tables.
            - Important from [[Data Governance]], [[Data Discovery]], [[Access Control]], [[Data Lineage]] perspectives
        - Collect Statistics
            - `ANALYZE TABLE...`, `COMPUTE STATISTICS FOR COLUMNS...`
            - Benefit: Query optimizer can utilize these stats to do it's job
        - Automate [[Schema Evolution]]
            - Enable MergeSchema in pipelines and ensure metastore sync
        - For non- [[Delta Table]], register using [[Hive Metastore]]
            - `CREATE EXTERNAL TABLE`
        - Leverage [[Unity Catalog]] Lineage #[[Data Lineage]]
        - Fallback of pure [[Delta Lake]] for prototypes, but plan to on-board into [[Unity Catalog]] or [[Hive Metastore]] before going live.

- Problem Definition for [[Medallion Architecture]] ((68e3e9de-a67a-4dcd-a9d0-f25d181e892f))
    - Start with the End-user need ((68e3ebf0-170c-4425-a34b-5231293310ad))
        - Example:
            - > Show me my weekly sales by region, product line and customer segment
        - ^^Gold^^ Data #[[Gold Layer]]
            - ^^Highly Curated:^^ All joins, aggregations and derivations done
            - ^^Conformed:^^ Same Dimensions and Metrics across dashboards
            - ^^Fast:^^ Ready for BI tools, data science, ML scoring (inferencing)
    - Source (Raw) Data ((68e3ec0a-f9af-46d9-8d30-6c1ee5f5e064))
        - Examples
            - Event Logs (clickstreams, transactions)
            - Third Party Feeds (CRM exports, partner API's)
            - Sensor / Device dumps (IoT telemetry)
            - DB snapshots (full or incremental inserts)
        - Typically landed ^^as-is^^ into a ^^Bronze^^ zone #[[Bronze Layer]]
    - Process from Raw to Gold: ((68e3f257-d79f-4265-9824-cf5e79c85f58))
        - Steps
            - Clean
            - Enrich
            - Transform
            - Conform & Optimize
        - Options 
          id:: 68e3f3e1-f1b4-4e7f-90b4-96e0afd0206a
            - ((68e3f406-f5aa-47e9-bb8c-ac6ac5bc8457))
            - Monolithic [[ETL]] job
                - One gigantic script: ingest --> clean --> enrich --> publish
                - Slow iterations, brittle code, hard to debug
            - [[ELT]] in a [[Data Warehouse]]
                - Load everything into [[Snowflake]] or [[AWS Redshift]] and then SQL transforms
                - High storage/compute costs, limited streaming support
            - [[Microservices]] or [[Event Stream]]
                - Each service publishes cleansed events downstream
                - Complex service orchestration, [[Tight Coupling]]
            - Custom in-app analytics
                - Each app writes directly to it's own reporting tables
                - Data silos, inconsistent definitions across apps
        - None of the above ((68e3f3e1-f1b4-4e7f-90b4-96e0afd0206a)) give us all these together:
            - Incremental, Reliable pipelines
            - Clear [[Separation of Concerns]] (landing vs. cleaning vs. serving)
            - Easy reprocessing when logic changes
        - [[Medallion Architecture]]
            - At any point of time, you can rebuild your silver and gold tables
            - Each layer can scale independently (remember ((68e3cf96-f01b-4168-a6ca-fb018e5c7930)) )
